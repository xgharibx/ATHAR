## Executive assessment

The app has a substantial offline-capable feature set, and its existing visual design remains intact. This audit fixed regressions across Quran navigation, persistence and restore, prayer-time fallback, auth callback delivery, sync lifecycle, audio, reminders, widgets, and content handling. The latest local web verification passes **1,041 tests in 141 files**, with **88 lint warnings and zero lint errors**; the TypeScript/PWA build succeeds, and Android debug assembly and lint passed in the preceding phase. All eight Android API 36.1 instrumentation tests passed in the earlier audit run. The current source and generated debug/release manifests request only user-granted `SCHEDULE_EXACT_ALARM`; interactive widget mutations use a private receiver and reject uninstalled widget IDs. On 2026-10-03 the live Supabase project became reachable: five non-destructive access, quota, and RLS-performance migrations were applied, Companion v9 adds a shared daily spend reservation, Dorar protection and account-deletion updates were deployed, and direct leaderboard table/view reads were closed. Anonymous Companion requests still fail with 401 before any paid provider request. The revisioned cross-device sync client and additive protocol migration are now prepared locally; staging pgTAP and live auth/sync checks remain open, and no sync migration or client deployment has been applied to production. The full dependency audit reports 15 development-tree advisories (1 critical, 13 high, 1 moderate); `npm audit --omit=dev` reports none.

The app is **not ready for a public store release**. Remaining gates include signed-in end-to-end verification, the still-undelivered Quran translation service, the pending leaderboard identity guard and self-reported score model, Sign in with Apple while Google is offered, accurate provider privacy/retention and store disclosures, the non-bootstrappable migration chain, iOS device/store preparation, an explicit Android backup policy, and signed release artifacts. Companion now has a shared $1/day estimated reservation ceiling and a 250-request daily cap; signed-in live flow and provider-cost reconciliation still need verification. The account-deletion function is updated in production, but no real user deletion was performed. The unsigned macOS 26/Xcode build passed on c24faa3, but iOS device round-trips remain open. Android CI packages an unsigned release AAB for review and checks platform version parity; the next Play upload still needs a version code above 74 and a signed artifact.

## Open findings, ordered by release impact

### P0 — Protect paid AI access before exposing the endpoint

The deployed Companion function was still the old unauthenticated proxy, so the local protections were not actually protecting production. This was corrected on 2026-10-03: migration 20261003042909 creates private atomic usage counters, and function v8 validates the bearer session with Supabase Auth, reserves up to 30 requests per UTC day and 5 per rolling minute per account, reads bodies with a 256 KiB UTF-8 byte cap, limits browser origins, and bounds upstream requests to 60 seconds. An anonymous request with a valid message shape returned 401 sign-in-required. We did not send a signed-in request or test a paid provider response. Per-user quotas do not prevent farming many accounts; add and verify a global/provider spend cap, durable abuse controls, and alerts before public release. Never place provider secrets in browser build variables.

**Release gate:** use dedicated test accounts to verify authentication, atomic quota boundaries, parallel reservations, body caps, provider failure handling, and account deletion without touching real user accounts. Add a global/provider spend ceiling and alerts to address account farming and total exposure. Keep paid AI gated until those controls and signed-in behavior are verified. Never place provider secrets in browser build variables.

The current client sends the full conversation history and a generated context containing activity and prayer/Quran progress, profile preferences, inferred mood, local memory, and relevant local-library passages through Supabase to MiniMax when a reply is requested. The history/profile comments previously described data as device-only, which conflated local storage with model requests; those comments and the existing Companion helper text now describe the outbound flow. MiniMax's current API terms say inputs and generated content may be used to provide, maintain, develop, and improve its services; its API privacy policy says data is stored in the United States and retained as long as necessary or permitted.
