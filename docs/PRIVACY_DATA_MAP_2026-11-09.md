## Proposed Play category mapping

These are candidate answers for the exact current Play form, not proof of the accepted declaration. `C` = collected off device. `S` = shared outside an applicable exemption. Default to **not ephemeral** where provider retention has not been established. Purposes below are feature operation, account management, security/abuse prevention and personalization, mapped to the current form's equivalent choices.

## Sharing exceptions need recipient-specific evidence

- Supabase-hosted Auth/sync/proxy data is collected. Supabase describes itself as a processor of customers' application data under its [DPA](https://supabase.com/legal/dpa); hosting on behalf of the developer may qualify for the service-provider sharing exception. Its corporate website privacy notice does not itself govern customer application data.
- MiniMax's [API terms](https://platform.minimax.io/protocol/terms-of-service) allow inputs/outputs to improve services. Without a confirmed project agreement limiting it to processing exclusively on ATHAR's instructions, do not apply a blanket service-provider or no-training exemption. A conservative shared answer for AI messages/context is supportable; exact independent purposes still need confirmation. Its [API policy](https://platform.minimax.io/protocol/privacy-policy) describes US processing and purpose/legal retention, not a fixed deletion deadline.
- Public ranking outputs are automatically exposed, and there is no explicit opt-in gate. Do not assume that a user-initiated sharing exception covers all ranking uploads or public results.
- Explicit export/share or map-navigation actions may qualify as user-requested transfers when expectations/disclosure are clear. That exception does not make separate backend collection optional or absent.
- Aladhan/Overpass, browser/OS speech recognition, embedded YouTube, fonts/content CDNs each need actual retention/use evidence before claims of ephemeral processing, complete non-sharing, or marketing/analytics exclusion. A privacy-enhanced video hostname is not proof of no data collection.

## Retention and deletion limits to resolve

1. The authenticated `delete-account` endpoint deletes the Supabase Auth user; account-owned sync/profile/quota rows cascade. The current UI does not block deletion on flushing all pending sync data. No real-user deletion was performed in this review.
2. Production migration history includes `leaderboard_delete_account_data`, `account_delete_leaderboard_handoff`, and `leaderboard_profile_lock_order`. Verified ownership links allow the database to remove a leaderboard identity when no other linked account owns it; the profile-upsert lock now follows the same order as deletion. Unprovable legacy identities and shared identities are handled conservatively, so the public policy does not promise deletion of every historical ranking row. Live deletion behavior still needs a controlled account test.
3. Production has active daily pruning jobs: score events older than 7 days, alias audit older than 30 days, and rollups before the current calendar year. The event and rollup jobs both reported success on 9 November 2026. This bounds those retention windows but is not a hard database-size ceiling; user/profile growth can still increase total database usage.
4. No uniform inactivity purge was found for account data, leaderboard profiles/identity links/moderation, or aggregate Companion budget records. Per-account Companion request counters reset their daily counters but their rows persist until account deletion; aggregate budget rows have no automatic retention cleanup identified in the checked migrations.
5. Exact Supabase project region, gateway log retention, backup rotation and erasure after requests are unverified. MiniMax project-specific retention/training limits, audio platform retention and remote-content/provider practices are unverified. Ask the owner/providers for these facts; the page makes no zero-retention/no-training promise.
6. The public contact is confirmed; request ownership verification, processing deadlines and manual recovery for orphaned ranking identities still need an operational procedure. A valid privacy/deletion page does not itself fix the backend erasure gap.

## Official requirements consulted

[Google Play User Data policy](https://support.google.com/googleplay/android-developer/answer/10144311) requires a public, non-PDF policy, app identity/contact, data practices, security and retention/deletion disclosure, plus in-app and external deletion mechanisms for apps offering accounts. [Play Data safety guidance](https://support.google.com/googleplay/android-developer/answer/10787469) requires disclosures for off-device and pseudonymous data, distinguishes chat from other generated content, and reserves optional status for collection a user can actually decline. Source/category mapping above is an assessment of ATHAR's code, not Google's approval.
